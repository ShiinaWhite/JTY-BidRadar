# 设计说明（Design Notes）

本文档泛化整理 JTY-BidRadar 的关键设计决策与一次真实运行事故的复盘，
不包含任何真实站点数据、公告内容或账号信息。

## 1. 架构总览

```text
┌─ Source 1：HTML 列表站点监控（monitor.py）
│    列表页 → lxml 解析 → SQLite(announcements) 去重 → 详情解析 → 邮件
│
├─ Source 2：JSON API 站点监控（sgcc_monitor.py）
│    noteList → 内容级校验 → SQLite(sgcc_notices) 去重 → 详情
│    → 公告文件 ZIP → 递归提取(sgcc_extractor) → 邮件
│
├─ email_notifier.py：共享 SMTP 模块（标准库，凭据只读本机文件）
│
└─ Windows 任务计划程序：pythonw.exe 静默单轮运行，非常驻进程
```

两个数据源**完全独立**：独立主程序、独立表、独立日志，仅共享数据库文件与
邮件模块。任一数据源故障不影响另一个。

## 2. Source 1 可靠性设计（一次真实误报事故的复盘）

事故形态：旧版本首次初始化只记录第 1 页约 10 条公告（浅基线）。第一次出现
真正的新公告时，程序按设计执行补偿扫描（page 2~5）；第 2~5 页中一直存在、
但从未进入数据库的历史公告，其 article_id 对数据库而言全部未知，被旧逻辑
一律误判为 NEW——近 40 条历史公告被当作新公告发出了邮件。

事后核查：没有证据表明站点发生历史回填或排序异常。根因是浅基线与更深范围
补偿扫描的覆盖范围不一致（shallow baseline vs deeper compensation scan），
历史未知数据被误判成了新数据。

修复由三层机制组成：

### 2.1 深基线

首次初始化不只记录第 1 页，而是把回溯深度内（5 页 ≈ 50 条）全部公告的
**列表字段**入库为 `baseline`，不抓历史详情、不发邮件。基线深度与回溯
深度对齐，保证"初始化见过"与"回溯会见到"的范围一致。

### 2.2 历史保护

回溯遇到的未知公告按发布日期分级：

- `publish_date < 上次成功运行日期`（或无日期）→ 历史欠账，静默补入
  `baseline`，不抓详情、不通知；
- `publish_date >= 上次成功运行日期`（含同日）→ 真正 NEW 候选，走详情
  抓取与通知流程。

日期只做天级比较（站点时间戳只有天级精度），参照日期取 meta 表的
`last_success_at`，绝不使用本机猜测时间。

### 2.3 单轮熔断

单轮真正 NEW 超过阈值（默认 10）→ 视为站点改版等异常批量变化：本轮跳过
通知、发一封「监控异常」告警，**候选不写库**（下一轮自动重新检测，状态
可恢复）；恢复后告警标记自动重新武装。

### 2.4 通知状态机

```text
baseline：历史基线，永不通知
pending ：已入库待通知（SMTP 失败/未配置邮箱都停留在此）
sent    ：已成功发送
```

SMTP 明确成功才标记 `sent`；失败保留 `pending`，下一轮与新公告合并补发，
保证公告绝不因网络抖动丢失。

### 2.5 内容级页面校验

目标站点对越界页码/异常请求也返回 HTTP 200（附错误页 HTML），因此一切
有效性校验基于**页面内容**而非状态码：解析不到任何列表条目、详情正文
过短均视为失败，不污染数据库，详情失败下一轮自动重试。

## 3. Source 2 设计要点

### 3.1 软拦截防护

站点在请求头不完整时可能返回 `HTTP 200 + successful=true + count=0 +
noteList=[]`（软拦截），如果当作"今天没有公告"会漏报。对策：

- 校验器检查 `successful / resultValue / count>0 / noteList 非空` 全链路，
  任一不满足即抛软拦截异常，本轮判失败，**不更新任何水位**；
- 绝不添加 Cookie/token/动态参数，只使用公开接口 + 明示身份的 UA。

### 3.2 判新规则

公告唯一键 = `noticeId`，"见没见过"只由 ID 集合决定；发布时间仅作水位
记录与日志，不参与判新（同一秒可能发布多条公告）。回溯终止条件 =
某页至少包含一个已知 ID（连续性证明）。

### 3.3 附件递归提取

- 该站公告 ZIP 的本地头与中央目录编码不一致（UTF-8/GBK 混杂），标准
  `zipfile` 直读会失败，因此按中央目录偏移解析本地头原字节自行解码；
- 老式 `.doc` 通过 OLE `ObjectPool` 的 package 流与 `Ole10Native` 流还原
  嵌套文件（纯 Python，`olefile`）；DOCX 同时提取段落与表格；XLSX 全部
  工作表转文本；RAR 为可选能力（有外部工具才解包，否则 WARNING 不中断）；
- ZIP bomb 防护：递归深度 ≤ 5、条目数 ≤ 200、单文件 ≤ 100MB、累计 ≤ 300MB；
- 安全：还原文件统一写成 `extracted/{序号}_{净化文件名}`，绝不使用压缩包
  内路径直接拼接磁盘路径（防路径穿越）；
- **外壳哈希陷阱**：该站 ZIP 每次下载字节都不同（服务器动态打包），附件
  变化检测必须以内部文件 SHA-256 清单为准，不能比较 ZIP 外壳哈希；
- 附件解析失败不静默：`partial/failed` 状态入库并在邮件中明确标注。

## 4. 请求纪律

- 全局步速控制：相邻请求最小间隔（串行、低频、对站点友好）；
- 明示身份的 User-Agent（普通浏览器 + 程序标识），不伪造指纹；
- 失败重试有上限，绝不狂重试；单轮运行限时（任务计划程序 30 分钟）。

## 5. 凭据与隐私

- SMTP 授权码只存本机 `data/email_secrets.json`，保存时用 `icacls` 关闭
  继承、仅保留当前用户；日志只记录异常类名，绝不打印配置内容；
- 邮件配置未就绪时通知静默降级（公告保留 pending），绝不因缺配置丢数据。

## 6. 测试策略

- 全部离线：`FakeFetcher` 映射 URL → fixture，`FakeSMTP` 捕获/注入失败，
  0 网络请求、0 真实邮件；
- fixture 全部为**合成最小页面/合成 Office 文档**，只复刻目标站点的 DOM
  结构与文件形态，不含真实公告内容——仓库本身不携带任何真实数据；
- 覆盖矩阵：解析/去重/基线/回溯上限/异常页/迁移幂等/状态机/SMTP 失败
  补发/同秒多公告/软拦截/嵌套提取/RAR 降级/ZIP bomb/内部哈希/表隔离；
- 唯一例外：老式 `.doc` OLE 嵌套结构无法纯 Python 合成，对应场景以本地
  私有样本（`tests/fixtures_local/`，不入库）可选启用。

## 7. Source 1 关键词相关性筛选（source1-rule-v1）

筛选只决定「是否发送通知邮件」，绝不决定「是否抓取/是否保存」：
所有真正的新公告都会抓详情、完整入库；被判为 C（明显不相关）的公告
`notification_status='filtered'`，不发邮件但可在数据库中审计。

设计约定：

- 纯函数模块 `source1_filter.py`：输入公告字段，输出 `FilterResult
  (level/score/reasons/version)`，不碰网络/数据库/邮件，便于独立测试与
  未来替换为 AI 分类；
- 文本来源权重：标题 > 正文（含资格要求/项目经理/业绩要求），不只看标题；
- 唯一关键词命中：同一关键词多次出现只计一次；一处文本中重叠/包含的
  命中取最长词（「110kV变电站」只计「变电站」），避免重复计分；
- 明确电压等级（0.4kV~1000kV、千伏汉字）为较强正向信号，每种不同等级
  只计一次；380V/220V 等低压仅弱正向（普通建筑电气常见）；
- 电力资质（电力工程施工总承包/输变电工程专业承包/承装（修、试）等）
  为很强信号，命中核心资质任意一个至少 B；
- 强制 A：标题命中强电力关键词 + 另一个独立强信号（电压/资质/另一强词）；
- 新能源/EPC 等上下文泛词只在同时存在真实电力信号时计分（封顶 +2），
  纯泛词（如「风电项目场区道路工程」）→ C；
- 负向词（装修/绿化/给排水等）仅在无任何强电力信号时计负分（封顶 -3），
  绝不做硬过滤——「变电站给排水改造」仍是高相关；
- 阈值：A score>=6；B 1~5；C <=0；宁可把边界公告放进 B；
- 邮件每条公告头部展示「相关性：A/B · 标签」与 3~5 个主要筛选依据，
  主题带等级（单条 `[JTY-BidRadar][A-高相关] …`，多条合并并计数），
  同一轮次始终只发一封；
- 部署顺序：先对数据库已有完整详情的公告做离线 shadow 分类
  （`scripts/shadow_filter_review.py`，只读），人工确认无误杀后再启用；
- 明确不做：已截止过滤、地区硬过滤、资格硬过滤（V1 范围之外）；
  历史 sent/baseline 数据不重新解释。
